# Web API認証の変遷：Cookie → JWT → BFF+Cookie

## 概要

Web APIの認証方式は、セキュリティとスケーラビリティの課題に対応しながら変遷してきた。
表面的には「Cookieへの回帰」に見えるが、実態はアップグレードされた構成である。

---

## 変遷の流れ

```
Cookie時代
  └─ サードパーティCookie規制で崩れる
        ↓
JWT + localStorage時代
  └─ XSSリスクとトークン無効化問題が顕在化
        ↓
BFF + HttpOnly Cookie時代（現代）
  └─ 両方の問題を解消した構成
```

---

## 各時代の詳細

### 1. Cookie時代（従来）

クロスオリジンのAPI呼び出しをCookieによるセッション管理で行っていた。

**問題点：**
- **サードパーティCookie規制**：異なるサイト間でCookieが共有されることで、ユーザーのブラウジング行動がトラッキングされるプライバシー問題が顕在化し規制が入った
- クロスオリジンAPI呼び出しにも影響（制限）が波及した
- サーバー1台前提の構成でスケールしにくかった

---

### 2. JWT + localStorage時代

サードパーティCookie規制への対応として、JWTをlocalStorageに保存してAuthorizationヘッダで送る方式が普及した。

**フロー：**
```
1. ログイン → サーバーがJWTを発行してクライアントに返す
2. クライアントはlocalStorageにJWTを保存
3. API呼び出しのたびに Authorization: Bearer {JWT} ヘッダに乗せて送る
4. サーバーは署名を検証するだけで認証完了（DBへのセッション問い合わせ不要）
```

**JWTとは：**
- 署名付きトークン。それ自体がペイロード（ユーザー情報など）を持つ
- サーバー側にセッションを保存しなくてよい（**ステートレス**）
- ステートレスにより、サーバーが複数台に増えてもセッションDBを共有する必要がなく**水平スケールしやすい**

**問題点：**

| 問題 | 内容 |
|---|---|
| XSSリスク | localStorageはJavaScriptから常にアクセス可能なので盗まれる |
| 無効化できない | 盗まれたJWTを有効期限切れまで止める手段がない |
| フロントが複雑 | トークンの保存・更新・ヘッダ付与を全部クライアントが管理 |

**補足 - ステートレスのトレードオフ：**

| メリット | デメリット |
|---|---|
| サーバー側セッション管理不要 | XSSで盗まれるリスク |
| 水平スケールしやすい | 盗まれたトークンを無効化できない |
| 実装がシンプル | 有効期限まで被害が続く |

**補足 - localStorageにはHttpOnly/secure属性は存在しない：**

HttpOnly・secure属性はCookieの属性であり、localStorageには適用できない。
localStorageに置く限り、XSSリスクは原理的に排除できない。

| 保存場所 | HttpOnly | secure |
|---|---|---|
| Cookie | ✅ 設定可能 | ✅ 設定可能 |
| localStorage | ❌ 存在しない | ❌ 存在しない |

---

### 3. BFF + HttpOnly Cookie時代（現代）

BFF（Backend For Frontend）を立てて、JWTをサーバー側に隔離する構成。

**構成図：**
```
ブラウザ
└─ HttpOnly + secure属性のCookie（セッションIDのみ）
        ↕
BFF（Cloudflare Workersなど）
└─ セッションIDに紐づくJWT・ユーザー情報をサーバー側で管理
        ↕
バックエンドAPI
```

**HttpOnly + secure属性の効果：**
- **HttpOnly**：JavaScriptからCookieにアクセス不可 → XSSで盗まれにくい
- **secure**：HTTPS通信のみでCookieを送信 → 通信経路での盗聴を防止

**なぜセッションIDだけを持つのか：**

Cookieには**セッションID（ランダムな文字列）のみ**を格納する。ユーザー情報やJWT本体はBFF側で管理。

| 比較 | 盗まれた場合の被害 |
|---|---|
| JWTが盗まれる | トークン自体にユーザー情報が含まれるので即情報漏洩、有効期限まで使い放題 |
| セッションIDが盗まれる | それ単体では情報は得られない、かつサーバー側でセッションを即時無効化できる |

**セッションID無効化の仕組み（Cloudflare Workers + KVの例）：**

セッションIDとユーザー情報の対応表をKVストアで管理し、ログアウト時や不審なアクセス検知時にエントリを削除する。

```
セッションID: "abc123" → { userId: 1, jwt: "...", 有効期限: "..." }
セッションID: "xyz789" → { userId: 2, jwt: "...", 有効期限: "..." }

"abc123"を削除 → そのセッションIDでのアクセスは即時不能
```

| | セッションID方式 | JWT単体 |
|---|---|---|
| 無効化 | サーバーのKV/DBから削除するだけ | 原理的にできない（有効期限まで有効） |
| サーバー負荷 | 毎リクエストでKV参照が必要 | 署名検証のみでOK |

---

## CORSだけでは不十分な理由

CORSはブラウザが自発的に守るルールであり、curlやPostmanなどブラウザ以外からは無視できる。
セッションIDが盗まれた場合、攻撃者はブラウザを介さずにBFFのエンドポイントを直接叩ける。

**CORSの役割：** 正規ブラウザからの不正オリジンを弾く補助的な防御  
**本質的な安全性：** サーバー側でセッションIDを即時無効化できること

両方を組み合わせた多層防御が正しいアプローチ。

---

## まとめ

「伝統的なCookieへの回帰」と言われるが、昔とは構成が異なる。

| | 昔のCookie運用 | 現代のBFF+Cookie運用 |
|---|---|---|
| スケール | サーバー1台前提 | Cloudflare WorkersなどEdgeで分散 |
| Cookie種別 | サードパーティCookieの問題あり | ファーストパーティのみ |
| 保護 | 属性管理が不十分なケースも | HttpOnly + secureで保護 |
| トークン管理 | クライアント側 | BFF（サーバー側）に隔離 |
| 無効化 | 困難なケースも | セッションIDをKVから削除するだけ |

**JWTとlocalStorageの組み合わせが抱えていたトレードオフ（スケーラビリティ vs セキュリティ）を、Cloudflare WorkersなどEdgeインフラがスケーラビリティ問題を解決したことで、セキュリティ優先の構成に振り直せるようになった**、というのが現代のBFF構成が広まった背景。
