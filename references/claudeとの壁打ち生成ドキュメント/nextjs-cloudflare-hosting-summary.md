# Next.js を Cloudflare でホスティングする際の面倒さ、その正体

参考記事: [続・貧者のアークテクチャ：Next.js + Cloudflare Workers + Turso 本番運用で踏んだ罠ぜんぶ](https://zenn.dev/nabettu/articles/a964f988e7cc75)

## 1. なぜ Cloudflare で Next.js を動かすのは面倒なのか

Next.js は Vercel（Node.js が素直に動く環境）を母艦に設計されているフレームワークである。そのため、Vercel から離れるほど「フレームワークの暗黙の前提」と「実行環境の制約」がぶつかりやすくなる。

ただし、これは「Vercel 以外＝面倒」という単純な話ではない。正確には **「Vercel 以外で、かつサーバーレス／エッジ環境で動かそうとすると面倒」** というのが実態。

- Docker + Node.js ランタイムで動かす普通のセルフホスト（VPS など）であれば、`next/image` も `"use client"` の関数呼び出しも問題なく動く
- 面倒さが噴出するのは、Cloudflare Workers のような「Node.js 非互換のランタイム」を選んだ場合

### 原因：V8 アイソレートという独自構成

Cloudflare Workers は **V8 アイソレート**（ブラウザの JS エンジンだけを取り出し、リクエストごとに軽量な実行コンテキストを起動する仕組み）で動く。Node.js が前提としてきたものと根本的に相容れない。

| Node.js の前提 | V8 アイソレートの現実 | 結果として起きる罠 |
|---|---|---|
| TCP 持続接続で DB プール | HTTP 経由のみ | SQL 1文 = HTTPS 1往復（レイテンシ増） |
| `sharp` 等のネイティブモジュールで画像処理 | ネイティブバイナリ不可 | `next/image` の最適化サーバーが動かない |
| プロセスが常駐する前提のグローバル状態 | リクエストごとに使い捨て（コールドスタート前提） | 状態保持には別の仕組み（Durable Objects 等）が必要 |
| サーバーのローカル TZ 設定 | 世界のどこで実行されるか不定 | UTC 固定によるサーバー・クライアントの表示ズレ |

参考記事内の罠のうち、`next/image`/`next/link` 不可、`"use client"` 関数呼び出しでの実行時 500、UTC 固定によるタイムゾーンずれなどは **Workers（V8アイソレート）特有の制約**。一方で RSC payload に select した列が全部乗る問題や、`unstable_cache` の JSON シリアライズの罠は **App Router / Next.js 全般に共通する落とし穴**であり、ホスティング先を問わず知っておく価値がある。

## 2. Cloudflare は独自構成のサービスが多い

Cloudflare は AWS や GCP のような「VPC・TCP 接続・プロセス常駐」という一般的なメンタルモデルが通用しにくい、独自のプログラミングモデルを持つコンポーネントが多い。

| サービス | 役割 | 特徴 |
|---|---|---|
| **Workers** | コンピュート（実行環境） | V8 アイソレート上で動くランタイム。リクエスト単位で軽量起動。AWS Lambda 相当だが、コールドスタートがほぼゼロという点で毛色が異なる |
| **KV** | キーバリューストア（キャッシュ寄り） | 読み取り多・書き込み少の用途向け。**結果整合性**（グローバル反映まで遅延あり） |
| **Durable Objects (DO)** | ステートフルな常駐アクター | 「1つの ID = 1つのインスタンス」が世界のどこか1箇所に生成され、メモリ上に状態を保持し続ける。強整合が必要な処理（WebSocket 接続の保持、排他制御など）向け |
| **R2** | オブジェクトストレージ | S3 互換 API。画像・動画などのバイナリ保存。エグレス（データ転送）無料が特徴 |
| **D1** | リレーショナル DB | Cloudflare マネージドの SQLite |

補足として、**KV と DO は対極の性質**を持つ。

- KV：どこからでも速く読めればよく、多少古くても許容できるデータ向け（結果整合性）
- DO：今この瞬間の状態が正確でないと困るデータ向け（強整合。ただし物理的に1箇所に集約されるため、遠いユーザーはレイテンシが伸びる）

Workers は「実行環境」というレイヤーであり、KV / DO / R2 / D1 はその上でデータを持たせる場所という位置づけ。Workers 自体はステートレスなので、状態を持たせたい場面でこれらのいずれかを選ぶ構造になっている。

こうした独自コンポーネントを一通り採用すると、AWS/GCP の一般的な設計知識がそのまま通用せず、「Cloudflare の作法」を丸ごと覚え直すコストが発生する。その代わり、1ベンダーで完結しデプロイが速い、というメリットとのトレードオフになる。

## 3. VPS・サーバーレス・フルマネージドの整理

### レイヤーの違い

| 種別 | 例 | 何を自分でやる必要があるか |
|---|---|---|
| **IaaS（VPS）** | エックスサーバー VPS、さくら VPS、AWS EC2 | OS セットアップ、Docker Engine のインストール、Nginx のリバースプロキシ設定、SSL 証明書、再起動時の自動起動、スケーリングなど全部自分で行う |
| **PaaS / サーバーレス** | Vercel, Netlify, Cloudflare Workers, Render, Railway | `git push` するだけでビルド・起動・スケーリング・SSL まで自動。裏側のサーバー管理は意識しなくてよい |
| **クラウド基盤（フルレンジ）** | AWS, Azure, Google Cloud | 素の VPS 相当（EC2 等）から、コンテナ実行（ECS/Fargate, Cloud Run）、サーバーレス（Lambda）まで幅広い選択肢が1社の中に揃っている |

VPS は一番下のレイヤー（自分でサーバーを組み立てる）であり、Vercel / Netlify / Cloudflare Workers はその上に乗った「組み立て済みの実行環境を借りる」サービス、という関係になる。AWS / Azure / GCP はこの両方（VPS 相当からフルマネージドまで）を自社メニューとして持っている。

### Vercel / Netlify と Cloudflare Workers の違い

- **Cloudflare Workers**：純粋なサーバーレス（V8 アイソレート、リクエスト単位起動、常駐プロセスなし）
- **Vercel / Netlify**：内部的にはサーバーレス関数の上に、フレームワーク特化のビルドパイプラインを被せた PaaS。Vercel は Next.js の開発元でもあり、`next build` の出力を自動で Vercel Functions / Edge Functions に振り分けてくれるため、ユーザー体験としては「サーバーレスであることを意識させない PaaS」に近い

いずれも「サーバーが常駐しっぱなしではない実行モデル」という点は共通しており、これが TCP 持続接続不可・V8 アイソレートの制約といった、今回話してきた罠の根本原因につながっている。

## 4. 共有ホスティング（静的ホスティング）でバックエンドが動かない理由

「FTP で静的ホスティング（エックスサーバー等の共有プラン）に Docker をアップロードすれば動くのでは」という発想は成立しない。**仕組みとして不可能**である。

- **FTP はファイル転送のみ**。ファイルを配置することしかできず、「プロセスを起動する」「ポートを開けてリクエストを待ち受ける」といった実行系の操作は一切できない
- 静的ホスティングは Apache/Nginx が HTML や PHP をリクエストの都度読んで返す仕組みであり、ユーザーが任意のプロセス（Node.js サーバーや Docker コンテナ）を常駐起動する権限がそもそも与えられていない
- Docker コンテナの実行には **カーネルレベルの機能（cgroups, namespaces）へのアクセス**が必要であり、root 権限のない共有ホスティング環境では技術的に不可能

| 環境タイプ | 例 | Docker / Node.js 実行可否 |
|---|---|---|
| 静的ホスティング（共有プラン） | エックスサーバー スタンダード、さくらの共有 | ❌ 不可（ファイル配信のみ） |
| VPS | エックスサーバー VPS、さくら VPS、ConoHa | ✅ 可（root 権限があり、SSH で Docker Engine をインストール可能） |
| PaaS | Render、Railway、Fly.io | ✅ 可（Git リポジトリや Dockerfile を push するとビルド・起動まで自動） |
| コンテナ専用サービス | AWS ECS/Fargate、Cloud Run | ✅ 可 |

バックエンド処理が必要な Next.js アプリを動かすには、**プロセスを起動・常駐させる権限を持つ環境**（VPS 以上）が最低条件になる。共有ホスティングで契約を持っている場合、そのままではバックエンド処理は原理的に実現できず、VPS プランへの契約変更、または Render / Railway のような PaaS への移行が必要になる。
